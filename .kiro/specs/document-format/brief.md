# Brief: document-format

## Problem
型付きの表形式データをファイルとして持ち運びたいが、既存の選択肢がどちらも要件を満たさない。xlsx はバイナリで意味のある差分が取れず、素の JSON には構造・型・シート概念の規約がない。結果として「データベースとして運用できて、かつ git でバージョン管理できる単一ファイル」が存在しない。

## Current State
グリーンフィールド。コードは一切存在しない。本スペックがプロジェクト全体の土台となる最初の1つ。

## Desired Outcome
File → Sheet → データスキーマ という構造（それぞれ 1 対 N）を持つドキュメントを、zip 圧縮された JSON テキストとして保存・読込できる。ファイルを開くとドキュメントモデルがメモリ上に構築され、保存すると決定的な（同じ内容なら必ず同じバイト列になる）zip が書き出される。テキスト差分が構造変更を素直に反映する。

## Approach
zip コンテナ内に、メタデータ・スキーマ定義・シートデータを別エントリとして分割配置する。行データは安定順序で整形し、JSON のキー順序を固定することで、git 差分が「変更した行だけ」を示すようにする。10 万行・全件オンメモリを前提とし、ストリーミング読み書きやページングは行わない（この単純化がスペック全体の規模を大きく下げる）。

## Scope
- **In**: zip コンテナ仕様、エントリレイアウト、ドキュメントモデル（File / Sheet / Schema / Row の ID 体系と関連）、シリアライズ / デシリアライズ、決定的出力の保証、フォーマットバージョニングとマイグレーションの枠組み、破損検出、zip 内に JSON 以外の形式（バイナリ添付など）を置くための拡張点
- **Out**: 型の意味論と検証（schema-engine）、UI 全般、git 操作（version-control）、遅延ロード / ページング / インデックス

## Boundary Candidates
- zip コンテナ層（バイト列の入出力）と ドキュメントモデル層（メモリ上の構造）の分離
- 永続化表現（ディスク上の JSON レイアウト）と インメモリ表現（編集に最適な形）の分離
- フォーマットバージョンのマイグレーション機構を独立させ、将来のスキーマ変更に耐えさせる

## Out of Boundary
- 型検証・型強制のルール（schema-engine が所有）
- 数式・再計算（formula-engine が所有）
- 履歴・コミット・差分表示（version-control が所有）
- 10 万行を超える規模のための遅延ロード（明示的な非目標）

## Upstream / Downstream
- **Upstream**: なし（プロジェクトの起点）
- **Downstream**: schema-engine, macro-runtime, version-control, export-templates, form-web-server — 実質すべてのデータ系スペック

## Existing Spec Touchpoints
- **Extends**: なし（新規プロジェクト）
- **Adjacent**: app-shell と並行して着手可能。両者は互いに依存しない

## Constraints
- Rust 実装。**`zip` crate は 2.3.0 以上を使うこと**（RUSTSEC-2025-0168: 展開時のシンボリックリンク経由の任意ファイル書き込み、1.3.0〜2.2.x が影響）。`zip-extract` / `zip_next` はメンテナンス終了フォークのため使わない
- git 差分親和性のため JSON は決定的整形（キー順序固定、安定した行順、改行位置の固定）が必須
- 10 万行 / 全件オンメモリ前提。それを超える規模は設計の想定外として明示する
- 個人・パワーユーザー向けのため、暗号化やアクセス制御はフォーマットに含めない
