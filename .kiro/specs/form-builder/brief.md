# Brief: form-builder

## Problem
型付きデータベースを持っていても、データを入れる手段がグリッドの直接編集しかないと、入力を他人に依頼できない。「コンポーネントを配置して簡易な入力フォームを作る」ことで、スキーマを知らない人でも正しい型のデータを投入できるようになる。

## Current State
schema-engine がスキーマを、schema-editor がその編集 UI を提供する。フォームという概念が存在しない。

## Desired Outcome
シートのスキーマからフォームの雛形が自動生成され、そこからコンポーネントをドラッグして配置・調整できる。フォーム定義はドキュメントの一部として保存される。フォームは配信されなくても、アプリ内の入力画面としてそのまま使える。

## Approach
スキーマ駆動を基本とし（フィールドを一から手で定義させない）、そこにレイアウトと表示の調整を重ねる形にする。コンポーネントの種類は schema-engine の型カタログから導出し、custom-types が登録した型も自動的に入力部品を持つ。フォーム定義は配信先（アプリ内 / Web）に依存しない中立な表現とし、レンダリングは form-web-server 側と共有する。

## Scope
- **In**: フォーム定義のデータモデル（配信先中立）、スキーマからのフォーム自動生成、コンポーネントの配置エディタ（ドラッグ&ドロップ、セクション、レイアウト）、コンポーネントの種類（テキスト / 数値 / 日付 / 選択 / 参照 / ネスト構造 / ファイル添付）、入力時のバリデーション表示、条件付き表示、アプリ内でのフォームプレビューと実入力
- **Out**: HTTP 配信・認証・書き戻しの並行制御（form-web-server）、スキーマ定義そのもの（schema-editor）

## Boundary Candidates
- フォーム定義モデル（データ）と フォームエディタ UI（作る側）と フォームレンダラ（使う側）の 3 分割
- レンダラを配信先中立に保ち、アプリ内表示と Web 配信の両方で再利用できるようにする
- コンポーネントレジストリを独立させ、custom-types が入力部品を登録できるようにする

## Out of Boundary
- HTTP サーバ・ネットワーク・認証（form-web-server が所有）
- スキーマの型定義（schema-engine / schema-editor が所有）
- 送信データの書き戻しにおける競合解決（form-web-server が所有）

## Upstream / Downstream
- **Upstream**: app-shell, schema-engine
- **Downstream**: form-web-server（本スペックが定義したフォームを配信する）

## Existing Spec Touchpoints
- **Extends**: なし
- **Adjacent**: schema-editor（型の編集と入力フォームの編集を混同させないよう UI 上の役割を明確に分けること）、custom-types（入力部品の登録インターフェースを共有）

## Constraints
- フォームレンダラは form-web-server で配信される Web ページ側でも動く必要があるため、Tauri の IPC に依存しない実装にすること
- 「簡易な」入力フォームであり、汎用のフォームビルダー製品を目指さない。requirements フェーズでコンポーネントの範囲を明示的に線引きすること
