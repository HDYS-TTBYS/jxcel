# Brief: version-control

## Problem
表形式データを扱う既存ツールでバージョン管理が事実上不可能なのは、ファイルがバイナリで差分が取れないためである。「いつ・誰が・どのセルを変えたか」が追えないまま重要なデータが編集され続けるのは日常的な痛みだが、これを解決した道具がほとんど存在しない。

## Current State
document-format が git 差分に適した決定的な JSON レイアウトで保存する。git 操作の層が存在しない。

## Desired Outcome
ファイルを作った時点で自動的にバージョン管理が始まっている（ユーザーが git を意識する必要がない）。編集履歴を時系列で辿れ、任意の 2 時点の差分が「どの行のどの列がどう変わったか」として表示される。過去の状態に戻せる。git を知っているユーザーは通常の git リポジトリとしても扱える。

## Approach
`git2-rs`（libgit2）を組み込み、ドキュメントの保存ディレクトリを git リポジトリとして管理する。生のテキスト差分ではなく、document-format のモデルを理解した構造的差分（行の追加 / 削除 / セルの変更 / スキーマの変更）を計算して表示する。個人利用が前提のため、初版ではリモート連携・マージ・コンフリクト解決は含めない。

## Scope
- **In**: リポジトリの自動初期化、保存時の自動コミット（およびコミット粒度の制御）、履歴の一覧と検索、構造的差分の計算と表示 UI、任意の時点への復元、名前付きスナップショット（タグ）、ブランチの基本操作、リポジトリのサイズ管理と圧縮
- **Out**: リモートへの push / pull、3-way マージとコンフリクト解決 UI、複数人の同時編集（すべて個人利用前提のため初版では非目標）

## Boundary Candidates
- git 操作の抽象層（libgit2 のラッパー）と 構造的差分の計算層の分離
- 差分計算（ドメイン）と 差分表示 UI の分離
- 自動コミットのポリシー（いつコミットするか）を独立させ、後から変更しやすくする

## Out of Boundary
- ドキュメントの保存形式そのもの（document-format が所有）
- チーム共有・リモート・マージ（将来のスペック候補として記録するのみ）

## Upstream / Downstream
- **Upstream**: document-format, app-shell
- **Downstream**: なし（ただし将来のチーム共有スペックの土台になる）

## Existing Spec Touchpoints
- **Extends**: なし
- **Adjacent**: document-format（決定的な出力が本スペックの差分品質を直接決めるため、両者の整合が最重要の継ぎ目）

## Constraints
- `git2-rs`（libgit2）を採用する。libgit2 は GPL-2.0 + リンク例外のため proprietary でも安全（libgit2 自体を改変した場合のみ改変版ソースの公開義務が生じる）。`gitoxide` は push / merge / rebase が未完成のため不採用
- **`git2` は 0.21.0 以上を使うこと**。2026 年に unsoundness advisory が 3 件（RUSTSEC-2026-0008 / 0183 / 0184、`Blame::blame_buffer`・`Remote::list`・`Buf` の null ポインタ参照）出ており、いずれも 0.21.0 で修正済み。古いバージョンへのピン留めをしないこと
- ドキュメントは 10 万行規模のため、1 回の保存で生じる差分が巨大にならないよう document-format のレイアウトと協調すること
- 自動コミットがリポジトリを肥大させないための方針（squash、GC）を設計に含める
