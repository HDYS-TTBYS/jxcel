# Brief: export-templates

## Problem
「エクセルやワードテンプレートへの連続書き出し」は、実務で最も需要が大きく、かつ既存ツールで最も面倒な作業のひとつ。請求書や報告書のテンプレートに対してデータを 1 件ずつ差し込み、100 件分のファイルを生成するといった作業が、現状ではマクロを自作するしかない。

## Current State
document-format と schema-engine が型付きデータを提供する。書き出す手段が存在しない。

## Desired Outcome
既存の .xlsx / .docx テンプレートを指定し、プレースホルダとシートの列を対応づけると、行数分のファイルが一括生成される。テンプレートの書式（フォント・罫線・画像）が保持される。マクロから書き出し処理を駆動することもできる。

## Approach
xlsx は `umya-spreadsheet`（既存ブックを開いてセルを書き換えられるためテンプレート差し込みに使える）を、新規作成は `rust_xlsxwriter` を使う。docx は Rust エコシステムにテンプレータが存在しないため（`docx-rs` は生ライターであってテンプレータではない）、template.docx の zip + OOXML に対してプレースホルダ置換を自前で実装する。この docx 部分が本スペック最大のリスクであり、最初に検証する。

## Scope
- **In**: エクスポート形式の共通基盤（出力先・命名規則・進捗・中断）、xlsx テンプレート差し込み、docx テンプレート差し込み（zip + OOXML プレースホルダ置換）、行データ → プレースホルダのマッピング定義 UI、繰り返し領域（表の行の展開）、連続書き出し（N 行 → N ファイル、または 1 ファイルに N セクション）、素の CSV / JSON / xlsx への単純書き出し、マクロから駆動するためのホスト API
- **Out**: 印刷 / PDF 化、テンプレートの作成・編集（外部の Office で行う前提）

## Boundary Candidates
- エクスポート基盤（ジョブ実行・進捗・命名）と 形式別ライタ（xlsx / docx / csv）の分離
- テンプレート解析（プレースホルダの発見）と 差し込み実行の分離
- マッピング定義（データ）と マッピング編集 UI の分離

## Out of Boundary
- テンプレートファイル自体の編集機能
- PDF 出力（将来のスペック候補）
- インポート（読み込み方向は本スペックの対象外）

## Upstream / Downstream
- **Upstream**: document-format, schema-engine
- **Downstream**: なし

## Existing Spec Touchpoints
- **Extends**: なし
- **Adjacent**: macro-runtime（マクロから書き出しを駆動するためのホスト API をここで公開する）、formula-engine（計算結果を書き出す）

## Constraints
- **docx テンプレート差し込みが最大のリスク**。Rust に成熟したテンプレータが存在せず、zip + OOXML の自前実装になる。design フェーズで「自前実装」と「小さな外部ヘルパープロセス」を比較評価すること
- OOXML のプレースホルダは Word によって複数の run に分割されることがあり、素朴な文字列置換では動かない。この問題への対処を設計に含める
- 100 件規模の連続書き出しで UI が固まらないこと
