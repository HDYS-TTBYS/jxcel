  - 地域設定や実行環境によって結果が変わりうる解釈は行わず違反とする

- [x] 6.2 書き込み経路ごとの判定を実装する

  - 編集経路では違反を報告したうえで、呼び出し元が保持できる値を返す
  - 収集経路では受け入れられないという判定を返す。**送信を止める処理は行わない**
  - 違反する値の位置と理由をいつでも取得できる経路を通す
  - 行を跨ぐ性質（一意性と参照の実在）はここでは判定しない。一括経路が持つ
  - 編集経路が拒否を返さないこと、収集経路が違反つきの受理を返さないことが型の上で保証されている
  - 1 セルの判定が 16 ミリ秒以内に返ることを**テスト内の計測として**確かめる。CI の予算ゲートには載せない（1 セルの判定は予算に対して桁違いに小さく、ゲートにする価値がない）
  - _Requirements: 6.1, 6.2, 6.3, 6.4, 10.2_
  - _Depends: 5.1, 6.1_

- 2.1 の申し送り（4.1 / 4.2 / 5.1 が読むこと）: `TypeKind::accepts` は `AcceptedVariants::Delegated`（`custom`）に対して**適合を返す**。これは変種段階の判断であり、実際の 2 値判定は `CustomType::validate`（4.1）が持つ。`Delegated` を適合の確定と解釈してはならない。また `CellValue::Null` は変種段階で常に適合（受理の可否は列の `required` が決める）。

- 2.1 の申し送り: qlty の rustfmt は `pub mod` をアルファベット順に並べる。宣言順を固定したい場合はコメントで意図を残すこと。
- **2.2 の裁定（4.2 / 5.2 / 5.1 / 7.x が読むこと）**: `DecimalDigits::fits` は**書かれた形の桁数**で判定する。すなわち `decimal(2,1)` は `"1.5"` を適合、`"1.50"` を違反とする（値は同じ）。これは意図した挙動である — `Decimal` は**逐語で往復する**契約を持ち、保存される文字列を書き換えられないため、宣言より長い小数表記を黙って受理すると「表記が宣言に合わない値」が残る。丸めも情報の損失になる（要件 7.2）。design は適合規則を明記していないが、この選択は「情報が失われる変換をしない」と整合する唯一の側である。
- 2.2 の申し送り: `types::decimal` の公開面は `DecimalDigits`（宣言と `accepts`）/ `DecimalScan` + `scan` / `DecimalCanonical` + `canonicalize` に分かれている。design のコンポーネント表は `DecimalDigits` を「桁検査・正準化・順序」と要約しているが Rust のインターフェースは固定していない。
- 2.2 の申し送り: 正準形は**宣言された scale に依存しない値厳密形**であり、順序の全順序を与える（design の記述より強い。`scale` を要しない）。
- 2.2 の申し送り: `DecimalDigits::new` は `precision >= 1 && scale <= precision` を要求し `Option` を返す。`SchemaError` に 10 進数の桁数専用の変種は無いため、3.1 / 3.2 は `None` を `MalformedDeclaration` へ落とす（位置と理由を運べる唯一の変種）。
- 2.2 の申し送り: 文法外の `CellValue::Decimal`（例 `"abc"`）は違反になる。`ViolationReason` では `PrecisionExceeded { expected: Expected::Decimal { precision, scale }, actual }` が該当する。
- 2.2 の既知の非ブロッキング所見: `decimal.rs` の `impossible_digit_declarations_are_rejected` に同一の assert が 1 行重複している。
- **2.3 の裁定（5.2 が読むこと）**: `datetime` 列の一意制約の比較は **`TemporalValue` の `Eq`/`Ord`（= 瞬時）** で行う。`2026-09-12T10:30:00+09:00` と `2026-09-12T01:30:00Z` は**同じ値であり重複**である。正準表記は書かれたオフセットを保つため文字列比較では同じ瞬時が別物になるが、それは `offset: required` の列でオフセットを変えるだけで一意制約を回避できること意味し、一意性の目的に反する。`offset: forbidden`（civil）の列では `Eq`/`Ord` が暦・時計の成分比較になり、同じ結論になる。
- 2.3 の申し送り: 受理は**正準表記との厳密一致**である（`accepts` は値を書き換えず `canonical() == 入力`）。jiff が寛容に受理する `20260912`・空白区切り・小文字 `t`/`z`・`+0900`・`+09`・`+00:00`/`-00:00`・末尾が 0 の小数部（`.0` / `.50`）は**すべて違反**になる。オフセット 0 を書けるのは `Z` だけである。
- 2.3 の申し送り: 正準表記は書かれたオフセットを保つ（`+09:00` のまま）。したがって `canonical()` は「同じ値の同一綴りへの正規化」では**ない**。
- 2.3 の申し送り: 閏秒 `:60` は丸めずに拒否する。オフセットの範囲は jiff に委譲する（`±24:00` は受理、`±26:00` は拒否）。
- 2.3 の申し送り: `TemporalValue` の瞬時フィールドは公開されており、3 つ組を整合させて組み立ててよいのは `parse` だけである。
- 2.4 の申し送り（3.2 / 4.4 / 5.1 が読むこと）: 文字列の長さは**文字数**（`chars().count()`）で数える。バイト長ではない（日本語が 3 倍に数えられるため）。例外はパターンの生文字列長で、これは **UTF-8 バイト長**（`regex` の推奨どおり生テキスト量を制限する）。
- 2.4 の申し送り: 利用者が書いたパターンは `regex` 標準の**部分一致**として評価する。値の全体一致を求める宣言は `^…$` を書く。5.1 が `Expected::Pattern` / `ViolationReason::PatternMismatch` を組み立てるときはこの意味論で説明する。
- 2.4 の申し送り: パターンの上限は 3 種（生文字列長 1024 バイト / コンパイル後 64 KiB / 入れ子の深さ 32）。超えるものは `SchemaError::PatternLimitExceeded { position, limit, observed, max }`（`limit` は `PatternLimit`）。**文法エラー（`[a-`、`(unclosed`、`a{2,1}`、`*`、グループ名の重複）は深さ違反と誤分類せず** `MalformedDeclaration` へ落とす。後方参照・先読みを含むパターンは `regex` がコンパイル時に拒否する。
- **3.1 の裁定（3.2 / 3.3 / 4.4 が読むこと）— 未知キーの扱い**: 型オブジェクト・列オブジェクトの中で文法が定義しないキーは **`SchemaError::MalformedDeclaration { position, reason }` として拒否する**（要件 1.7「解釈できない構造を含むときは位置と理由を含むエラーとして拒否する」）。**黙って読み飛ばしてはならない** — 読み飛ばすと「宣言 → テキスト → 宣言」の往復で内容が落ち、要件 1.4 / 3.3 が壊れる。宣言側に未知フィールドの保持機構は作らない（design は payload 側の前方互換を「未知の `kind` を**その列だけ使用不能**に落とす」で解いており、`DeclaredKind::Unknown` がそれを実装している。新しい**型**の追加が現実的な進化の道であり、新しい**キー**の追加は `Revalidation Triggers` が挙げる文法変更として扱う）。
- **3.1 の裁定（`custom` の任意パラメータ）**: `custom` の型オブジェクトが持てるのは `kind` と `type` だけである。design のカタログ表が言う「その任意のパラメータ」は**拡張型の実装が持つ**ものであり、design の `CustomType` トレイトはパラメータを受け取る口を持たない（`id` / `validate` / `validate_batch` / `canonicalize` のみ）。読む手段の無いパラメータを宣言に載せない。`custom-types` が宣言経由のパラメータを必要とするなら、design が `Revalidation Triggers` に挙げる「`CustomType` トレイトのシグネチャ」の変更としてトレイトと文法を同時に足す。
- 3.1 の申し送り: `FieldDecl` は `description` を持つ（design のフィールド例には無いが、列と同じ鍵集合に揃える）。3.3 は列と同じ相対位置（`default` の後）で出力する。
- 3.1 の申し送り: `Schema` は `columns` のみを持ち、型定義の集合を持たない（集合は上流エンベロープ `SchemaPart::type_defs` が所有。design「Out of Boundary」）。`TypeDefinition { id, definition }` 1 件を表す型は宣言側にあり、**集合を組み立てるのは compile 層（4.3 / 4.4）**である。
- 3.1 の申し送り: `Constraints` は**平坦な構造体**である（種別ごとの意味を持たない位置も設定できる。例 `bool` に `choices`）。3.2 は「その種別で意味を持たない位置」を**拒否する**（黙って無視しない）。理由は上と同じ（往復で内容差になる）。
- 3.1 の申し送り: `TypeDecl::{Kind { kind, constraints }, Ref(TypeDefId)}` により「`kind` と `$ref` の両方を持つ／どちらも持たない」型は Rust の型として構成できない。codec は構文の段（`kind` と `$ref` が同時に現れる JSON）で拒否する。
- 3.1 の申し送り: `DeclaredKind::{Known(TypeKind), Unknown(Box<str>)}` が未知の `kind` トークンを保持する（要件 11.7 の前提。compile がその列を使用不能にする）。
- **3.2 の裁定（5.1 / 4.4 が読むこと）**: 型オブジェクト・列オブジェクトの文法は**閉じている**。未知キーは `MalformedDeclaration`（位置と理由つき）で拒否し、黙って読み飛ばさない。未知の `kind` トークンだけは `DeclaredKind::Unknown` として保持する（要件 11.7。compile がその列を使用不能にする）。
