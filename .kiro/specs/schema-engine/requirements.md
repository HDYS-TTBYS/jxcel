# Requirements Document

## Project Description (Input)
シートに対してネスト構造を持つスキーマを宣言でき、セルへの入力・マクロからの書き込み・フォームからの送信のすべてに対して同一のルールで検証と型強制が働く、実行時の型エンジンを実装する。

「DB のようなデータ型を指定できる」「ANY もあり」「JSON のようにスキーマをネスト可能」という要件は、表示上の書式設定ではなく、値を検証し・強制変換し・不正なデータを拒否する実行時エンジンを必要とする。これがないと本アプリは「型付きデータベース」ではなく単なる JSON エディタになる。

**現在地**: document-format は実装完了しており、ドキュメント構造（File / Sheet / Schema / Row）は揃っているが、スキーマの意味論は意図的に空けてある。本スペックは次の継ぎ目を引き継ぐ。

- スキーマ・ペイロードは document-format にとって**不透明**である。エントリ `schemas/<sheet-ulid>.json` のエンベロープ形 `{ "root": <opaque>, "types": [ { "id": "<ULID-26>", "definition": <opaque> } ] }` は document-format が所有するが、`root` と `definition` の中身は解釈されない。抽出されるのは型定義の識別子と `{"$ref": "<ターゲット>"}` という参照マーカーの出現だけであり、**型の意味論と `$ref` の解決規則は本スペックが所有する**
- セル値は閉じた 8 変種（`CellValue`: Null / Bool / Int / Float / Decimal / Text / Nested / Attachment）。「どの列がどの変種を使うか」「`Decimal` の桁数と有効性」は document-format 側が明示的に本スペックへ委ねている
- document-format の `migration` は**形式バージョン**（`major.minor`）の移行であり、本スペックの「スキーマ変更時のデータ移行」とは別物である
- 決定的 JSON 出力と未知フィールドの保持は document-format が所有済みであり、スキーマ宣言の表現はその上に乗せるだけでよい

**アプローチ**: JSON Schema の思想（ネスト・合成）と RDB の型カタログ（厳密な型・NOT NULL・既定値）を組み合わせた独自スキーマを定義する。スキーマ宣言（データ）と検証エンジン（実行）を分離し、宣言をコンパイル済みバリデータに落とすことで 10 万行の一括検証を実用速度にする。ユーザー定義型のための拡張点をここで切り、実装は custom-types に委ねる。

**スコープ（In）**: 組込型カタログ（数値 / 文字列 / 真偽 / 日時 / 列挙 / 参照 / ANY など）、ネスト（object / array）、null 許容・必須・既定値・一意制約、検証エンジンと検証エラーの表現、型強制ルール（文字列入力からの解釈を含む）、スキーマ変更時のデータ移行、シート間参照の整合性、ユーザー定義型のための拡張インターフェース定義

**スコープ（Out）**: JS によるユーザー定義型の実装（custom-types）、スキーマ編集 UI（schema-editor）、セルの表示書式・エディタ選択（data-grid）、数式による計算列（formula-engine）、UI 全般

**制約**: Rust 実装で、Tauri を知らない純粋なライブラリとして実装・テストできること。10 万行の全件検証が実用時間で終わること。ANY 型が存在するため型システムは「全てが厳密」を前提にできず、ANY を含む値のマクロ側での扱いを設計で明示すること。スキーマ自体もドキュメントの一部として git 差分に乗るため、宣言表現は人間可読かつ決定的であること。
