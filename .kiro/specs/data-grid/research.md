# Research & Design Decisions: data-grid

## Summary
- **Feature**: `data-grid`
- **Discovery Scope**: New Feature + Complex Integration（実装済みの 3 スペックの上に載り、拡張点を 2 つ新設する）
- **Key Findings**:
  - **`document-format` に行の削除と位置指定の挿入が存在しない。**変更 API は `add_row`（末尾追加）・`reorder_rows`・`set_row_values` のみで、要件 6.2 は現状の公開面では実現できない
  - **開いた `Document` をメモリ上で保持する持ち主がどこにも存在しない。**`document-format` に依存するクレートは `schema-engine` だけであり、`app-shell` は「他のドメインクレートに依存しない」と明記している。この欠落に対して新スペック `document-session` を roadmap へ追加した
  - **グリッドライブラリの現実解は 1 つに絞られる。**範囲選択とクリップボードが無償で使えて canvas で描く MIT のライブラリは Glide Data Grid だけであり、その stable は React 19 を受け付けない
  - **描画の失敗を web ページ側から確実に検出する手段は存在しない。**WebKit は WebGL のレンダラ文字列を伏せるため、要件 12.2 は「塗って読み戻す」検査で満たすほかない

## Research Log

### グリッドライブラリの選定
- **Context**: `brief.md` は選定を design で行うと定めた。`tech.md` は Glide Data Grid を「stable が止まっている」ことを理由に第一候補から外している。要件 11.1（毎秒 60 回の描画更新）と要件 7（範囲のコピーと貼り付け）を無償の許諾で満たす必要がある
- **Sources Consulted**: npm registry / GitHub API（2026-09-13 取得）、各プロジェクトの LICENSE と価格表、1771 Technologies の 2026-06 のベンチマーク
- **Findings**:

| 候補 | 版 / 日付 | 許諾 | 描画 | 範囲選択・貼り付け | React 19 | 判定 |
|---|---|---|---|---|---|---|
| Glide Data Grid | stable 6.0.3 / 2024-02-03、beta 6.0.4-alpha24 / 2025-10-08、最終コミット 2026-01-21 | MIT | canvas | あり（`getCellsForSelection` / `onPaste`） | **stable は不可**（peer が 18.x まで。issue #1189 が open）。beta のみ可 | **採用（beta に固定）** |

| RevoGrid | 4.27.10 / 2026-09-09 | MIT（中核） | DOM | あり（貼り付けは未確認） | **公式の表明なし**（devDeps は React 18 固定） | 次点 |

- **Implications**:
  - DOM 系（AG Grid / RevoGrid / TanStack）は 2026-06 の実測で 10 万行規模で毎秒 27〜38 回まで落ちており、要件 11.1 に届かない見込みが強い。**30 列 × 可視 40 行で毎フレーム 1,200 要素**を扱うことになる
  - 本設計は並べ替え・絞り込み・行モデルを Rust 側に置くため、**ライブラリに求めるのは描画・当たり判定・文字計測・クリップボードの配管だけ**になる。Glide の `getCellContent` は引きに来る形であり、窓単位の転送とそのまま噛み合う
  - Glide は並べ替えと絞り込みを**持たない**（公式に「データ源の側で実装せよ」）。本設計にとってはこれは欠点ではなく一致である

### Linux / WebKitGTK 上の canvas
- **Context**: roadmap の Prototype-First Risk #3。`tech.md` は「描画失敗を検出する API は存在せず、Tauri も wry も回避策を自動設定しない」と記録している
- **Findings**:
  - 症状は白画面・リサイズ時のちらつき・`Failed to create GBM buffer` で、原因は WebKitGTK の DMA-BUF レンダラ。**2.42 以降**が該当し、NVIDIA のプロプライエタリドライバとソフトウェア GL で再現する。WebKit 側の bug 262607 は **WONTFIX** で解決済みであり、上流の修正は来ない
  - 最新の再現報告は WebKitGTK 2.52.3（`tauri-apps/tauri#15936`、2026-08-29）。**DOM は検査器に見えているのに何も塗られず、ログも出ない**
  - 回避は環境変数のみ。順に `__NV_DISABLE_EXPLICIT_SYNC=1` → `WEBKIT_DISABLE_DMABUF_RENDERER=1` → `WEBKIT_DISABLE_COMPOSITING_MODE=1`
  - 一方で canvas の描画自体は改善している。2.46 が Cairo から Skia へ、2.50 が Skia のスレッド化、2.52 が 2D canvas の動的 MSAA と描画命令の一括再生を入れた。Ubuntu 22.04 は 2.50.4、24.04 は 2.52.6 を配っている
- **Implications**: canvas を選ぶこと自体は 2026 年時点で不利ではない。危険なのは描画基盤の初期化であり、**起動直後に描画が成立したことを自分で確かめる**設計が要る

### 描画成立の検出可能性
- **Findings**:
  - `WEBGL_debug_renderer_info` の `UNMASKED_RENDERER_WEBGL` は一般的な手段だが、**WebKit は指紋対策のためこの文字列を伏せる**。Tauri 自身の文書がそう明記している。本製品の Linux と macOS はいずれも WebKit であり、この手段は使えない
  - WebGL2 のコンテキスト生成はソフトウェアラスタライズでも成功し、信号が出ない。**Canvas 2D に至っては GPU 支援の有無を問う API が存在しない**
  - 実用的に効くのは 3 つ: (1) 既知の図形を塗って `getImageData` で 1 画素読み戻す、(2) 起動時に合成的な走査を行いフレーム時間の中央値を測る、(3) Rust 側から環境変数と GL の素性を読む
- **Implications**: 要件 12.2 は (1)、要件 12.3 は (2) で満たす。(3) は `app-shell` の要件 10.3 が既に所有しているため**本機能は重複して持たない**

### 上流の公開面の実地確認
- **Context**: 要件 3・6・7 が `document-format` の変更 API に依存する
- **Findings**（`crates/document-format/src/model/mod.rs` を直接確認）:
  - 存在する: `add_sheet` / `remove_sheet` / `rename_sheet` / `set_sheet_columns` / `set_root_schema` / `add_row` / `reorder_rows` / `set_row_values` / `add_attachment`
  - **存在しない**: 行の削除、位置を指定した挿入、セル単位の設定、変更通知、未保存の追跡
  - 書き込みの粒度は**行まるごと**（`set_row_values` が `Vec<CellValue>` を置き換える）。1 セルの編集は行を読んで写して書き戻す形になるが、列数は 30 程度なので費用は無視できる
  - `Row` は `Serialize` も `Clone` も持たず、`Violation`（`crates/schema-engine`）も `Serialize` を持たない。`CellValue` は `Serialize` / `Deserialize` を持つ（`crates/document-format/src/value.rs`）。それでも境界を越えられないのは 64 ビット整数（`CellValue::Int`）と識別子を出せず、ts-rs の derive が `crates/app-shell/src/ipc/` の下だけに許されるためであり、直列化できないからではない
- **Implications**: `document-format` に足すのは行の削除・位置指定の挿入・取り除いた行の差し戻しの 3 つだけである（design.md「上流への最小の追加」）。それ以外は既存の公開面で足りる

## Architecture Pattern Evaluation

| 選択肢 | 内容 | 強み | 危険 / 限界 | 判定 |
|---|---|---|---|---|
| 全件をフロントエンドへ運ぶ | 10 万行を一度に webview へ送り、JS 側で並べ替え・絞り込み・描画 | 走査中の往復が皆無で、描画が滑らか | ドキュメントが Rust と webview に二重に載る。要件 11.6 に反する。`structure.md`「性能はドメイン側で守る」に反する | 却下 |
| **窓単位で運ぶ（採用）** | 並べ替え・絞り込み・違反集計を Rust 側に置き、可視範囲の窓だけを生バイトで送る | 資源が行数に比例しない。判定の源が 1 つに保たれる | 走査中に往復が入るため、先読みを誤ると引っかかる | **採用** |
| 行ごとのコマンド | セルや行を個別に取得する | 実装が単純 | `bulk.rs` の module doc が「この経路に行指向の API は無い」と明示的に禁じている | 却下 |

## Design Decisions

### Decision: 描画層を移植口の背後に置き、Glide Data Grid を beta 版に固定して採用する
- **Context**: 要件 11.1 を満たす描画と、要件 7 の範囲コピー・貼り付けを、無償かつ proprietary 配布と両立する許諾で得る必要がある
- **Alternatives Considered**: 1) Glide を直接使う 2) 自前 canvas を最初から書く 3) DOM 系ライブラリ
- **Selected Approach**: 描画・当たり判定・クリップボードの配管だけを担う**移植口**を本機能が定義し、その実装として Glide Data Grid `6.0.4-alpha24` を使う
- **Rationale**: 本設計はデータ・並べ替え・絞り込み・検証をすべて Rust 側に置くため、ライブラリに委ねる面積が小さい。移植口を挟む費用は薄く、上流が止まっている危険に対する退路になる
- **Trade-offs**: alpha 版への固定を受け入れる。stable は React 19 を拒否するため選択肢がない。MIT なので取り込み（vendoring）は合法であり、規模も現実的
- **Follow-up**: **タスクの最初期に、WebKitGTK 上で 10 万行 × 30 列の走査を実測する。**ここで毎秒 60 回に届かない場合、同じ移植口の背後に自前 canvas を置く判断へ切り替える

### Decision: 境界に数値を出さず、表示文字列と変種の札で運ぶ
- **Context**: `ipc-contract.md` が 64 ビット整数の越境を禁じている。`CellValue::Int(i64)` と `RowId`（ULID/u128）はいずれも JS の数値に収まらない
- **Selected Approach**: 窓の応答は「行識別子（生の 16 バイト）・セルの表示文字列・値の変種の札・違反の有無」の並びとする。**数値としての値は一切越えない**
- **Rationale**: グリッドは値を表示し、利用者が打った文字を返すだけでよい。型解釈は `schema-engine` が所有しており、フロントエンドが数値として解釈する理由がない。これにより 64 ビット問題が構造的に消える
- **Trade-offs**: 桁区切りや小数点の表示規則が Rust 側に寄る。フロントエンドでの並べ替えができなくなるが、並べ替えはもともと Rust 側に置く
- **Follow-up**: 入れ子の値だけは構造を持つため、`document-format` の `to_json_bytes` / `from_json_bytes` を使って JSON 文字列として往復させる

### Decision: 取り消し履歴を Rust 側に置く
- **Context**: 要件 9.7 は、数式の再計算とマクロの実行が同じ履歴に加わることを求める
- **Selected Approach**: 履歴は `crates/data-grid` が所有し、命令と逆命令の対を積む
- **Rationale**: `formula-engine` と `macro-runtime` はいずれも Rust 側で動く。履歴をフロントエンドに置くと、後から乗る 2 者が境界を越えて履歴を操作することになり、拡張点として成立しない
- **Trade-offs**: 取り消しのたびに境界を 1 往復する。1 操作あたり 1 回なので要件 11.3 の 100 ミリ秒に収まる

### Decision: 上流の欠落は 3 メソッドの追加に閉じる
- **Context**: 行の削除と位置指定の挿入が `document-format` に無い
- **Selected Approach**: `remove_rows(sheet, &[RowId]) -> Result<Vec<Row>, _>` と `insert_row_at(sheet, index) -> Result<RowId, _>` に加え、取り除いた行をそのまま差し戻す `insert_rows_at(sheet, index, Vec<Row>) -> Result<(), _>` を追加する。`remove_rows` が取り除いた行を返すのは、取り消しに値と識別子の両方が要るためである（`Row` は `Clone` を持たず、既存行の識別子・値を書き換える口も無い。空の行しか作れない `insert_row_at` では取り消しを満たせない。詳細は design.md「上流への最小の追加」）
- **Rationale**: 一括で受けるのは、範囲削除が 1 操作であり、行ごとに呼ぶと並びの作り直しが繰り返されるため。決定的出力の契約には触れない
- **Trade-offs**: 実装済みのクレートへ手を入れる。影響は行の集合と並びに閉じており、往復の契約は変わらない

### Decision: ドキュメントの保持を新スペックへ切り出す
- **Context**: 開いた `Document` の持ち主が存在しない
- **Alternatives Considered**: 1) `data-grid` が吸収する 2) `app-shell` を拡張する 3) 新スペック
- **Selected Approach**: `document-session` を roadmap へ新設し、`data-grid` はその下流になる
- **Rationale**: `app-shell` は「他のドメインクレートに依存しない」制約を持つため 2) は制約を壊す。1) は「表示と操作」と「ファイルの寿命管理」という異質な責務を同居させ、`version-control` が保存に相乗りする時点で切り直しが必要になる
- **Trade-offs**: MVP の本数が 2 本から 3 本に増える。`data-grid` の実装は `document-session` の完了を待つ

## Risks & Mitigations
- **Glide Data Grid が WebKitGTK で毎秒 60 回に届かない** — 移植口の背後で自前 canvas へ切り替える。判断はタスク最初期の実測で行い、設計全体には波及させない。**1.6 で実測し、採用のまま進める判断を下した**（本ファイル「実測: 10 万行 × 30 列の走査中のフレーム時間」）
- **alpha 版への固定** — 版を固定し、`Cargo.lock` と同じ規律で `package-lock.json` を追跡する。取り込みが必要になった場合に備え、移植口が触る面を最小に保つ
- **窓の先読みが外れて走査が引っかかる** — 先読みの幅と窓の大きさを計測で決める。フレーム時間の標本を要件 12.3 の検出と共用する
- **`document-session` の契約が未確定のまま設計する** — 本設計は「ウィンドウに対応する `Document` への参照と、変更を書き戻す手段」という能力の水準でのみ依存し、API の形を先に決めない。`document-session` の design 確定時に本設計を再検証する（Revalidation Trigger に記載）

## 実測: 10 万行 × 30 列の走査中のフレーム時間（タスク 1.6）

**これは 1.6 の判断点の記録である。** 使い捨ての画面 `smoke-glide-probe`（10 万行 × 30 列の
Glide Data Grid）を**実際に起動**し、末尾まで走査しながら `requestAnimationFrame` の間隔を
標本に取り、中央値を測った。計測器は
`src/features/smoke/glideProbeMeasure.ts`、画面は `src/features/smoke/glideProbe.tsx`、
段の実体は `scripts/check-render-traversal.sh` と
`scripts/ci/{linux,macos,windows}/verify-render-traversal.*`（**一時的な段**。恒久の観測は
9.2 / 9.3 が担い、その時点で取り除く）。

### 計測の条件（1.6 の要求をそのまま満たす）

- **走査は末尾まで届いている。** 333 フレームで `到達行=99999 / 行数=100000`（1 フレーム
  300 行）。**部分的な走査の数値ではない。**
- **標本の基準を一緒に記録する。** フレーム数 333、行数 100000、列数 30、到達行を毎回出す
  （中央値だけでは何に基づく数か分からないため）。
- **塗って読み戻す検査が成立している。** 既知の色 `rgb(17,205,238)` を塗って 1 画素を読むと
  **`17,205,238,255`** が返る（要求どおりの `塗り=ok`）。加えて**標本の面の canvas の色数を
  数え**、52〜59 色（1 なら一様＝何も塗られていない）であることを確かめている —
  **「DOM はあるが何も塗られない」症状**（下記の DMA-BUF の欠陥）を捕まえるためである。

### 実測値（中央値 ms / p90 / 最大。60 Hz の閾値は 16.67 ms）

**Linux・実画面（Wayland・GPU。`webkit2gtk-4.1` は 2.52.6）。** 最も忠実な Linux の計測:

| 回避の環境変数 | 中央値 | p90 | 最大 | フレーム数 | 到達行 |
|---|---|---|---|---|---|
| なし | **17.00** | 17.00 | 18.00 | 333 | 99999 |
| `__NV_DISABLE_EXPLICIT_SYNC=1` | **17.00** | 17.00 | 17.00 | 333 | 99999 |
| ＋`WEBKIT_DISABLE_DMABUF_RENDERER=1` | **24.00** | 27.00 | 30.00 | 333 | 99999 |
| ＋`WEBKIT_DISABLE_COMPOSITING_MODE=1` | **24.00** | 28.00 | 32.00 | 333 | 99999 |

**Linux・CI ランナーの方式（Xvfb。ソフトウェアラスタライズ）。** `scripts/check-render-traversal.sh`
を丸ごと実行して得た値:

| 回避の環境変数 | 中央値 | p90 | 最大 | フレーム数 | 到達行 |
|---|---|---|---|---|---|
| なし | **17.00** | 17.00 | 19.00 | 333 | 99999 |
| `__NV_DISABLE_EXPLICIT_SYNC=1` | **17.00** | 17.00 | 18.00 | 333 | 99999 |
| ＋`WEBKIT_DISABLE_DMABUF_RENDERER=1` | **17.00** | 18.00 | 20.00 | 333 | 99999 |
| ＋`WEBKIT_DISABLE_COMPOSITING_MODE=1` | **18.00** | 19.00 | 23.00 | 333 | 99999 |

> **【独立レビューによる訂正】上の Xvfb の表は、回避の条件について再現しなかった。**
> 同じ検査器を同じ開発機の Xvfb で走らせ直すと、**どの X のバックエンドが選ばれるか**が
> 支配的で、`GDK_BACKEND=x11` を明示した場合は **6.00〜7.00 ms**（3/3）、自動選択では
> **24.00 ms**（3/3）であり、記録した 17 → 18 の並びにはならなかった（`なし` の行も含めて
> 再現していない）。計測そのものは実在した（生の行は残っている）が、当時の起動の
> 綴りは再現できず、**値の再現性が無い**。
>
> **したがってこの表の数値を根拠に何かを主張しない。** Xvfb について言えるのは
> 「CI の段が走り、値を記録する」ことまでである。**判定に効く regime は実画面であり**、
> そちらは独立に 5/5 で再現した（上表）。むしろ分かったのは、**実画面の vsync を持たない
> 仮想ディスプレイでは回避の条件どうしが比較できない**ということであり、これは
> **実画面を拘束条件に選んだ判断を強める**（1.6 の明文どおり）。

**Windows / macOS の数値は無い。** 1.6 の明文（「Windows と macOS の数値は 9.2 の観測で
確かめる」）に従い、両 OS の段は**走査の画面がその OS で描画されること**だけを確かめ、
数値は 9.2 へ送る（下記「測れなかったこと」を参照）。

### 中央値 17.00 ms の読み方（これが判断の要である）

**17.00 は 16.67 をわずかに超えるが、要件を外した証拠ではない。** 理由は計測した:

- **`performance.now()` の刻みが 1.00 ms である**（計測器が毎回 `時計刻みms=1.00` を出す）。
  WebKit は指紋対策として時刻の精度を粗くする（本ファイル「描画成立の検出可能性」に同じ
  事情がある）。60 Hz の表示周期 16.67 ms は、**1 ms 刻みの時計では 17 ms として現れる**。
  **ただし 17.00 という値だけでは ≤ 16.67 を証明できない** — 1 ms 刻みでは 17 は
  およそ [16.5, 17.5) のどの値でもありうる。したがってこの論法は単独では決め手にならない。
- **分布が二峰ではない。** 「中央値 17」は、全フレームが 17 の場合と、半分が 17 で半分が 33 の
  場合のどちらでも成り立つ。**p90 も最大も記録した** — 17.00 / 18.00〜19.00 であり、
  **落ち込むフレームが実質無い**（333 フレームの走査で最大でも 19 ms）。
  これは真の値をおよそ **[16.67, 17.2] ms** に挟む（1 本でも 33 ms が混ざれば中央値か p90 が
  動く）。

**独立レビューは、時刻の刻みに依らない測り方でも閾値を確かめた。** 同じ表示面で
**総経過 / (フレーム数 − 1)**（テレスコープ平均。1 ms 刻みの影響を受けない）を測ると
**16.68 ms** であり、表示面は `xrandr` の実測で **59.97 Hz**（周期 16.67 ms）だった。
さらに**重い負荷**を掛けると量子化された中央値は 19 / 63 ms へ動いた — すなわち
**1 周期に収まらないフレームは隠れない**。したがって記録した分布は
**「60 Hz に同期している」と「60 fps をわずかに下回る」を実際に区別している**。

したがって**素の条件（回避なし）は毎秒 60 回の描画更新を維持している**と読む。

### 回避の環境変数は走査を遅くする（実画面で 17 → 24 ms）

**実画面（Wayland/GPU）では、DMA-BUF レンダラを切ると中央値が 17.00 → 24.00 ms へ悪化する**
（p90 27、最大 30。60 Hz を割る）。これは DMA-BUF が**実際に効いている**ことの裏付けであり、
`crates/app-shell/src/render_fallback.rs` が採用している `LINUX_POLICY`
（`WEBKIT_DISABLE_DMABUF_RENDERER=1`）に**代償がある**ことを実測で示す（同ファイルの表が
「高速描画経路（ゼロコピーの DMABUF）を捨てる」と述べているとおりである）。**Xvfb では
この差を主張しない** — 仮想ディスプレイには実画面の vsync が無く、上記の訂正のとおり
条件どうしが比較できないためである（独立レビューの実測でも、支配的なのは X のバックエンドの
選択であって回避の条件ではなかった）。

**この計測は `render_fallback.rs` の採用を見直す根拠にはならない** — 回避策は
「描画が成立しない環境」でのみ印に従って適用され、描画が成立する環境では何も起きない
（要件 10.3 の「無条件には適用しない」）。ここで分かったのは**適用されたときの代償**である。

### 採否の判断（7.2）

> **採否: 採用（Glide Data Grid を移植口の背後に置いたまま進める）。自前 canvas への切り替えは
> 行わない。**

- **閾値**: 要件 11.1「毎秒 60 回の描画更新」→ **中央値 ≤ 16.67 ms**。
- **拘束条件（Linux）の実測**: 素の条件で**中央値 17.00 ms、p90 17.00、最大 19.00**（333
  フレーム、10 万行を末尾まで走査、塗りの読み戻し成立）。時計の刻み 1.00 ms を踏まえると
  **16.67 ms に張り付いており、閾値を満たす**。さらに**時刻の刻みに依らないテレスコープ平均
  16.68 ms**（59.97 Hz の表示面で実測）が同じ結論を独立に支える（上記「中央値 17.00 ms の
  読み方」）。
- **確度**: **中〜高**。実画面の Linux（Wayland/GPU、WebKitGTK 2.52.6）の数値は**独立のレビューが
  5/5 で再現**し、塗りの成立も確かめた。**確度を下げている要因**は次の 2 つ:
  1. **Xvfb は要求した表示経路ではない。** CI の Linux の段はソフトウェアラスタライズであり、
     research.md が扱う危険（DMA-BUF/GPU の経路）とは**別の regime** である。実画面の数値を
     ローカルの開発ホストで取れたことでこの差は埋めたが、**CI はその regime を再現しない**
     （CI の緑を実画面の証拠と読み替えてはならない）。
  2. **走査は `scrollTo` による行番号の跳躍であり、利用者のホイール操作ではない。**
     実際の操作はホイールの刻みと慣性に依存する。1.6 の文言（「10 万行を走査」）には合うが、
     9.2 / 9.3 の実操作の観測で確かめる価値がある。
- **維持する条件（切り替え判断の引き金）**: 次のいずれかが起きたら 7.2 の切り替えを再検討する
  — ①9.2 の 3 OS の観測で中央値が 16.67 ms を明確に超える、②9.3 の実操作の観測で走査が
  引っかかる（本ファイル「窓の先読みが外れて走査が引っかかる」の緩和策と併せて）、
  ③一時的な段が取り除かれた後、DMA-BUF の欠陥（tauri#15936）が再発する版へ上がる。

### 測れなかったこと（正直な記録）

- **macOS / Windows の数値は無い。** 計測の行は**アクセシビリティの木**（AT-SPI。`busctl` で
  読む）から取る。**macOS の WKWebView と Windows の WebView2 には AT-SPI が無い**（AT-SPI は
  D-Bus 上の仕組みである）。1.6 の明文が両 OS の数値を 9.2 へ送っているので、段は**走査の
  画面がその OS で描画されること**だけを確かめる（`scripts/ci/macos/verify-render-traversal.sh`
  と `scripts/ci/windows/verify-render-traversal.ps1`）。**この 2 段が緑でも要件 11.1 の
  両 OS の証拠にはならない。**
- **フロントエンドからアプリの診断記録（`TargetKind::Folder`）へ書く経路は無い。** 実測:
  wry は webview の console を stdout へ流さず、`tauri-plugin-log` に `TargetKind::Webview` は
  無く、`document.title` もネイティブの題名へ伝わらない（`on_document_title_changed` を誰も
  配線していない）。したがって計測の行は**アクセシビリティの木**（DOM の `aria-label`。実測で
  AT-SPI の名前として読めた）へ出す。**この制約は 7.6（`RenderProbe`）と 9.3（劣化の記録）に
  引き継がれる** — 9.3 は「新しい記録の仕組みを作らない」と定めているので、劣化を器の診断へ
  記録するには**既存の記録経路**（`emit` → feature で括った listener など）を使う必要がある。
- **Xvfb 上の Linux の段はソフトウェアラスタライズである**（上記の確度の項）。CI ランナーには
  `xvfb` しか無い（`scripts/ci/linux/install-system-deps.sh`）ため、**CI では実画面の GPU 経路を
  再現できない**。この差は本節が明示して埋めるものであり、覆い隠すものではない。
- ~~**開発ホストで Linux の段の反証を最後まで走らせられなかった。**~~ **独立レビューが閉じた。**
  開発機の Xvfb（`/tmp/xvfb-root` の `Xvfb` と `xvfb-run`）を使って Linux の段を**最後まで実行**し、
  `LINUX_STEP_RC=0`（4 条件＋反証）を得た。検査器単体の反証も、配布物の AppImage を渡して
  rc=1（「走査の計測の行を読めませんでした」）で成立し、**ウィンドウが観測されたこと**も
  確かめられている（起動していない検査は 0 でも緑になるため）。判定の閉じた枝（`unmeasurable`・
  `塗り=ng`・画素不一致・`色数=1`・到達行不足など 7 つ）もパッチした写しで実演された。

### 計測の副産物（要件 11.2 の最初の画面）

段を走らせるついでに、走査の画面の**初回描画の成立までの経過**も記録された（8.2 の成立行の
`経過=`）: 実画面（Wayland/GPU）で **187〜217 ms**、Xvfb で **約 690〜710 ms**。
いずれも要件 11.2 の **1 秒の内側**である。**これは要件 11.2 の判定ではない** — 11.2 の予算は
「起動から最初の画面まで」であり、判定は 9.3 が実画面の観測で行う（ここでの値はその予備である）。

### 変更したアプリの状態（記録）

計測に先立ち、`WEBKIT_DISABLE_DMABUF_RENDERER=1` を適用した起動を 1 回行った（回避策の
代償を測る条件）。その後、描画が成立した起動で `render.fallback` の印は下り、
`~/.local/share/com.jxcel.app/settings.json` は `{"render.fallback":false,…}` に戻っている。

## 実測: 移植口の実装（GlideAdapter）の操作の観測（タスク 7.2）

**これは 7.2 の受け入れ（見え方の主張）の記録である。** 7.2 の文言は「10 万行のシートを走査でき、
選択した範囲が視覚的に区別でき、列幅と列の位置が操作できる」であり、**canvas に描かれるか**の
主張である。単体テスト（`vitest`。`environment: "node"`）は写像と配管しか固定できないので、
`tech.md`「GUI・配布物・プラットフォーム差を含む主張は、実物を起動して観測した結果で
裏付けること。単体テストは回帰の網であって受入の証明ではない」に従い、**実物を起動して観測した**。

観測の実体は、1.6 の段と同じ形の**使い捨ての面と段**である。

| 何 | どこ |
|---|---|
| 駆動する面（移植口を実物の DOM の上で動かす） | `src/features/smoke/portProbeAdapter.tsx` |
| 画面（検証専用の初期画面 `smoke-port-probe`） | `src/features/smoke/portProbe.tsx` |
| 観測の行の形（純粋な関数） | `src/features/smoke/portProbeFacts.ts` |
| 検査器（起動 → アクセシビリティの木から 1 行 → 判定） | `scripts/check-port-interaction.sh` |
| 3 OS の段（**一時的**。9.2 / 9.3 が取り除く） | `scripts/ci/{linux,macos,windows}/verify-port-interaction.*` |

### 観測の方法（**本物と同じ経路を通す**）

移植口（`createGlideAdapter().mount(container, spec)`）をマウントし、利用者の操作を**DOM の
イベントとして**注ぐ。走査は移植口の口（`handle.scrollTo`）であり、残りはポインタと
クリップボードである。

| 主張 | 注いだもの | 読んだもの |
|---|---|---|
| 走査 | `handle.scrollTo({row: 99999, column: 0})` | `scrollTop` / 内容の高さ / 到達行 / 塗りの読み戻し / 色数 |
| 選択 | canvas への `pointerdown` → `pointermove` → `pointerup`（セル (1,0) から (3,1) へ） | 移植口の `onSelectionChange`、**同じ画素の色**、選択として印されたセル数 |
| 列幅 | 列 1 と列 2 の境界への `pointerdown` → +120 px の `pointermove` → `pointerup` | 移植口の `onColumnResize`、**内容の幅**（変更の前後） |
| 列の移動 | 列 2 の見出しへの `pointerdown` → `pointermove`（20 px 以上）→ 列 0 の上 → `pointerup` | 移植口の `onColumnMove`、**描かれている見出しの並び** |
| 複製 | canvas への `copy` イベント | 移植口の `onCopy`、クリップボードからの読み戻し |
| 貼り付け | canvas への `paste` イベント（文字列を載せた `DataTransfer`） | 移植口の `onPaste`、**送った文字列と受け取った文字列の一致** |

**観測の行はアプリの診断記録ではなくアクセシビリティの木（AT-SPI）から読む**（フロントエンドから
診断記録へ書く経路が無い。上記「測れなかったこと」と同じ制約であり、1.6 の段と同じ経路である）。

### 実測（Linux・実画面。WebKitGTK `AppleWebKit/605.1.15`）

実行した綴り（開発ホスト。`GDK_BACKEND=x11` は**この環境でウィンドウを X11 の木に見せる**ためで
あり、判定には使わない — 1.6 の独立レビューが Xvfb について記録したのと同じ事情である）:

### 読み方（**どの値がどの主張を支えているか**）

1. **10 万行を走査できる。** `到達行=99999`（= `行数 - 1`）であり、`scrollTop=3399616` は
   `scrollHeight - clientHeight = 3400036 - 420` に**一致する**（末尾に着いている）。加えて
   塗りの読み戻しが成立（`塗り=ok 画素=17,205,238,255`）し、canvas の色数が 10 である —
   **「DOM はあるが何も塗られない」症状**（1.6 が記録した DMA-BUF の欠陥）を捕まえる対照である。
   40 万行ぶんの仮想スクロール（`scrollHeight=3,400,036` px）が実在し、その末尾のセルが
   **引かれている**（末尾は取得済みでない行なので、骨組みの棒が 124/192 画素で観測された）。
2. **選択した範囲が視覚的に区別できる。** 移植口が受け取った選択は `1:0-3:1`（3 行 × 2 列）で
   あり、アクセシビリティの木で 6 つのセルが選択として印され、**同じ画素の色が選択の前後で
   変わった**（`255,255,255,255` → `235,241,255,255`。白から選択の色へ）。**「同じ画素が変わった」
   ことが要点である** — 別の場所を見て「色が違う」と言うのではない。
3. **列幅と列の位置が操作できる。** 列 1 と列 2 の境界を掴んで 120 px 動かすと、移植口は
   `onColumnResize(1, 240)` を受け取り、**描かれた内容の幅が 3600 → 3720 へ 120 px 増えた**
   （= 変更が実際の描画に現れている）。列 2 の見出しを列 0 の上へ運ぶと、移植口は
   `onColumnMove(2, 0)` を受け取り、**描かれている見出しの並びが `列2,列0,列1,列3` になった**
   （= 並びが実際に変わっている）。増分が一致すること（幅）と、並びそのものを読むこと（移動）が、
   「移植口が知らせを受け取った」だけでは言えない**描画の変化**の証拠である。
4. **クリップボードの配管**（要件 7.1、7.2）。複製の範囲は選択と一致し（`1:0-3:1`）、
   23 文字の表形式が返り、貼り付けでは**送った文字列と受け取った文字列が 1 バイトも違わない**
   （`往復=一致`）。錨は選択の左上（`1:0`）である。

### 測れなかったこと（正直な記録）

- **クリップボードからの読み戻しは `不可` である。** `navigator.clipboard.readText()` が
  この環境では権限で拒否される（`クリップボード=不可`）。したがって**「システムのクリップボードに
  実際に載った」ことはこの段では証明していない** — 証明しているのは「移植口が返した文字列が
  クリップボードへ渡す経路まで届いた」（実装が `navigator.clipboard.writeText` を呼ぶ）ところまで
  である。**`不可` を `一致` と読み替えない**（読めなかったことを成立と数えない）。
- **ポインタの操作は合成のイベントである。** 本物のマウス・トラックパッドの慣性やホイールの
  刻みは通っていない。経路（DOM のイベント → Glide の聴取 → 移植口）は本物と同じであり、
  選択・幅の変更・並びの変更はその経路で成立した。**実操作での確認は 9.2 が担う。**
- **数値は Linux の 1 環境である。** macOS / Windows の段は**画面が描画されること**だけを確かめる
  （AT-SPI が無いため観測の行を読めない）。**数値の欠落を成立と読み替えない。**
- **単体テストは見え方を何も証明しない。** `glideAdapter.test.ts` が固定するのは写像と配管であり、
  実物の canvas は `vitest` の環境（`node`）に存在しない。**`jsdom` を足して canvas を模すことは
  していない**（模した DOM では見え方の主張を何も裏付けられない）。

### 副産物（実装の判断に効いた実測）

- **同じタスクで 3 つのポインタのイベントを続けて注ぐと操作が成立しない。**（実測: 選択は
  「列の全体の選択」になり、幅の変更と列の移動は無反応だった。）Glide の選択・並べ替え・幅の変更は
  **制御された props の再描画を挟んで進む**（掴んだ列や選択の現在値は React の状態として次の描画で
  届く）ので、駆動側は**フレームを跨ぐ**必要がある。本物の利用者の操作でも同じ順序になる。
- **列の境界を掴むときは境界そのものを掴む。** Glide は幅を「ポインタの位置 - 列の左端」で決めるので、
  境界から 2 px 内側を掴むと 2 px 足りない幅になる（実測: 120 px 動かして 118 px 広がった）。
- **列幅の変更と列の移動の反映は再マウントで行った。** `RendererHandle` に幅や順を押し込む口が
  無いという 7.1 の申し送りどおりであり、**移植口の契約（変化は次の `mount` の仕様に載る）を
  そのまま使っている**。
