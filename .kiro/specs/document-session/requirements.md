# Requirements Document

## Introduction

本機能は、**開いたドキュメントの寿命**と、**ドキュメントへの変更の唯一の経路**を所有する。`document-format` はファイルを読み書きする能力を持ち、`app-shell` はウィンドウとファイル選択を持つが、**開いた `Document` をメモリ上で保持する持ち主が存在しない**。`app-shell` は他のドメインクレートに依存しないため、`src-tauri` はウィンドウごとにファイルの位置を持つだけで、その位置からドキュメントを開かない。本機能はその穴を埋める。

ウィンドウ 1 つに対して開いているドキュメントが 1 つ対応し、そのドキュメントへの読み取りと変更は単一の経路を通る。未保存の変更があるかが分かり、ウィンドウを閉じる前に利用者へ問われる。保存の実行はファイル形式の側に委ね、本機能は**いつ・何を保存するか**だけを決める。

本機能は下流の土台でもある。`data-grid` / `schema-editor` / `macro-runtime` は変更を本機能の経路へ流し、本機能はその経路を**10 万行を跨ぐ一括の変更**を受けられる形で提供する。値の正否の判定は型システムが所有し、変更の意味論（何をどう変えるか）は変更を要求する機能が所有する。本機能は適用の口と、適用されたことの記録だけを持つ。

## Boundary Context

- **In scope**: ウィンドウ単位のドキュメントセッションの生成・保持・破棄、ウィンドウの生成要求にある位置からの読み込み、利用者が選んだファイルの読み込み、メモリ上のドキュメントの所有、読み取りと変更の単一の経路、10 万行を跨ぐ一括の変更の受け口、未保存の追跡、保存の実行と出所の管理、出所を持たないドキュメントの保存先の選択、未保存のときの閉じる前の問いとその提示、新規ドキュメントの作成、開いているドキュメントの名前と状態の提示、変更の適用・読み込み・保存の所要時間の予算、3 つの OS での観測

- **Out of scope**:
  - ファイル形式そのもの・決定的な出力・ファイルの構造（`document-format` が所有）
  - 値が型に適合するかの判断と型強制（`schema-engine` が所有）
  - 表示と編集の操作・取り消し履歴（`data-grid` が所有）
  - スキーマの宣言と変更（`schema-editor` が所有）
  - 変更履歴・差分・自動コミット（`version-control` が所有。本機能の保存に相乗りする）
  - ウィンドウの生成と破棄・題名・メニューの位置（`app-shell` が所有）
  - **アプリ全体の終了の可否**（`app-shell` が所有。終了操作は無条件に終了する。本機能は関与しない）

- **Adjacent expectations**:
  - 読み込みと書き出しの実体はファイル形式の側が所有する。本機能は位置と時機だけを決め、形式とバイト列を組み立てない。**形式の決定性は本機能の経路を通しても損なわれない**
  - 値の正否の判定は型システムが所有する。本機能は変更をそのまま受け取り、判定を代行しない
  - 変更の意味論（行の追加・値の置き換え・入れ子の編集など）は変更を要求する機能が所有する。本機能は適用の口と、適用されたことの記録だけを持つ
  - 起動時にウィンドウへ指定された位置は、シェルが保持するウィンドウの生成要求から読む。シェルは位置の中身に触れない
  - 終了前の問いは、シェルが既に持つ終了拒否の問い合わせ（閉じてよいかの往復）に答える形で成立する。**選択肢の提示は本機能が加える**（シェルは現在、拒否を記録に残すだけで何も提示しない）
  - 表示対象のシートを選ぶ手段と、シートを画面に描くことは本機能の外にある。本機能はどのドキュメントのどのシートが存在するかを与えるだけである
  - ドキュメントの保存に相乗りする変更履歴（`version-control`）は、本機能の保存の時点を観測できる必要がある。本機能は保存を 1 つの経路に閉じ、相乗りできる形にする

## Requirements

### Requirement 1: ウィンドウとドキュメントの対応
**Objective:** As a 複数のファイルを同時に開くユーザー, I want どのウィンドウにどのドキュメントが開いているかが一意に定まること, so that 窓ごとの作業が混ざらない

#### Acceptance Criteria
1. The Document Session shall ウィンドウ 1 つにつきドキュメントを高々 1 つ保持する。
2. When ドキュメントの位置を指定して作られたウィンドウが現れたとき、the Document Session shall その位置のドキュメントを読み込んでそのウィンドウに保持する。
3. When 利用者がウィンドウに対してファイルを選んだとき、the Document Session shall 選ばれたファイルのドキュメントをそのウィンドウに読み込む。
4. While あるウィンドウのドキュメントが保持されている間、the Document Session shall そのドキュメントへの読み取りと変更を、他のウィンドウを介さない同一の経路で扱う。
5. When ウィンドウが破棄されたとき、the Document Session shall そのウィンドウのドキュメントを破棄し、他のウィンドウのドキュメントと未保存の状態を変えない。
6. The Document Session shall 開いているドキュメントの名前と、そのウィンドウに未保存の変更があるかどうかを、外から読める形で与える。
7. The Document Session shall 保持しているドキュメントのシートの一覧（識別子と名前）を外から読める形で与える。
8. If ドキュメントを保持していないウィンドウへ読み取りまたは変更が要求されたとき、then the Document Session shall 要求を適用せずに失敗として報告する。

### Requirement 2: 読み込みの成否と差し替えの保護
**Objective:** As a 作業中のデータを失いたくないユーザー, I want 読み込みの失敗や差し替えで今の内容が壊れないこと, so that 失敗のたびに作業をやり直さずに済む

#### Acceptance Criteria
1. If 指定された位置のドキュメントを読み込めなかったとき、then the Document Session shall そのウィンドウの状態を変えずに、読み込めなかった理由を報告する。
2. While ウィンドウに未保存の変更があるドキュメントが保持されている間、the Document Session shall 同じウィンドウへの別のドキュメントの読み込みを拒否し、その理由を報告する。
3. If 読み込みが進行している間に同じウィンドウへ別の読み込みが要求されたとき、then the Document Session shall 進行中の読み込みの結果を壊さず、後から来た要求を失敗として報告する。
4. When ドキュメントを指定されずに作られたウィンドウでファイルが選ばれたとき、the Document Session shall そのファイルを読み込み、以後そのウィンドウのドキュメントとして保持する。
5. While あるウィンドウの読み込みが進行している間、the Document Session shall そのウィンドウの閉じてよいかの問い合わせに、待たせることなく答える。

### Requirement 3: 変更の適用の単一の経路
**Objective:** As a 大規模な台帳を編集するユーザー, I want 変更が必ず 1 つの経路を通り、一括の変更でも引っかからないこと, so that どの機能から触っても同じ結果になる

#### Acceptance Criteria
1. The Document Session shall 保持しているドキュメントへの変更を、そのドキュメントを保持するウィンドウを通した経路だけから受け取る。
2. When 変更が適用されたとき、the Document Session shall その変更を保持しているドキュメントに反映し、適用の結果を要求元へ返す。
3. If 適用を完了できなかったとき、then the Document Session shall 失敗として報告し、部分的な適用を成功として報告しない。
4. When 変更が適用されている間に同じウィンドウの読み取りが要求されたとき、the Document Session shall 適用済みの最新の内容を返す。
5. When 10 万行かつ 30 列のシートのすべてのセルを置き換える変更が 1 度に要求されたとき、the Document Session shall 1 秒以内に適用を完了する。
6. While あるウィンドウの変更の適用が進行している間、the Document Session shall 他のウィンドウへの読み取り・変更・開いているドキュメントの問い合わせを待たせない。
7. The Document Session shall 変更の適用の所要時間を、対象の行数に対して二乗で増加させない。

### Requirement 4: 未保存の追跡
**Objective:** As a 作業の途中でアプリを閉じるユーザー, I want 保存していない変更があることがつねに分かること, so that 変更を失う前に気づける

#### Acceptance Criteria
1. When ドキュメントへ変更が適用されたとき、the Document Session shall そのウィンドウを未保存として扱う。
2. When ドキュメントの読み取りだけが行われたとき、the Document Session shall そのウィンドウを未保存として扱わない。
3. While ウィンドウが未保存である間、the Document Session shall そのことを外から読める形で与える。
4. When ドキュメントの読み込みが完了したとき、the Document Session shall そのウィンドウを未保存でない状態にする。
5. When 保存が成功したとき、the Document Session shall そのウィンドウを未保存でない状態にする。
6. While ウィンドウが未保存でない間、the Document Session shall そのウィンドウを閉じてよいと答える。

### Requirement 5: 保存
**Objective:** As a 編集した内容を残したいユーザー, I want 保存が 1 つの指示で完結し、失敗しても内容が失われないこと, so that 保存の操作を迷わず行える

#### Acceptance Criteria
1. When 利用者が保存を指示したとき、the Document Session shall そのウィンドウのドキュメントを、そのドキュメントの出所の位置へ書き出す。
2. When 出所の位置を持たないドキュメントの保存が指示されたとき、the Document Session shall 保存先の選択を求め、選ばれた位置へ書き出して、以後その位置を出所とする。
3. If 保存先の選択が取り消されたとき、then the Document Session shall 何も書き出さず、そのウィンドウを未保存のまま保つ。
4. If 書き出しに失敗したとき、then the Document Session shall そのウィンドウを未保存のまま保ち、失敗の理由を報告する。
5. When 保存が進行している間に同じドキュメントへの変更が要求されたとき、the Document Session shall 書き出した内容と保持している内容が食い違わない順序で扱う。
6. When 10 万行かつ 30 列のドキュメントの保存が指示されたとき、the Document Session shall 2 秒以内に書き出しを完了する。
7. The Document Session shall 保存する内容を、ファイル形式の側の決定的な出力と同一に保つ（本機能の経路を通した保存のバイト列は、形式の側へ直接書き出したバイト列と一致する）。
8. When 保存が成功したとき、the Document Session shall 保存した内容を、以後の保存の出所と一致させる（同じ指示で同じ内容が書き出される）。

### Requirement 6: 閉じる前の問い
**Objective:** As a 未保存のまま窓を閉じようとしたユーザー, I want 閉じる前に選択肢を示されること, so that 保存し忘れで作業を失わない

#### Acceptance Criteria
1. When 未保存のドキュメントを保持するウィンドウを閉じようとしたとき、the Document Session shall 閉じてはならないと答え、その理由を与える。
2. When 閉じてはならないと答えたとき、the Document Session shall 利用者へ「保存して閉じる」「変更を破棄して閉じる」「閉じるのをやめる」の選択肢を提示する。
3. When 利用者が「保存して閉じる」を選んだとき、the Document Session shall 保存を行い、成功した場合に限り以後の答えを閉じてよいへ変える。
4. If 保存が失敗したか、または保存先の選択が取り消されたとき、then the Document Session shall 閉じてはならないという答えを保ち、その理由を示す。
5. When 利用者が「変更を破棄して閉じる」を選んだとき、the Document Session shall そのウィンドウを未保存でない状態にし、以後は閉じてよいと答える。
6. When 利用者が「閉じるのをやめる」を選んだとき、the Document Session shall ドキュメントと未保存の状態を変えない。
7. When 閉じてはならないと答えたあとに利用者が同じウィンドウを再び閉じようとしたとき、the Document Session shall その時点の状態に基づいて答え直す（前の答えを固定しない）。

### Requirement 7: 新規ドキュメントの作成
**Objective:** As a 台帳を新しく作り始めるユーザー, I want 空のドキュメントをその場で作り始められること, so that 既存ファイルを用意せずに作業を始められる

#### Acceptance Criteria
1. When 利用者が新しいドキュメントの作成を指示したとき、the Document Session shall そのウィンドウに、行も列も無いシートを 1 つ持つドキュメントを用意する。
2. When 新しいドキュメントが用意されたとき、the Document Session shall それを出所を持たない状態で、未保存の変更が無い状態から始める。
3. While ウィンドウに未保存の変更があるドキュメントが保持されている間、the Document Session shall そのウィンドウへの新規ドキュメントの作成を拒否し、その理由を報告する。
4. When ドキュメントを持たないウィンドウで新しいドキュメントが作られたとき、the Document Session shall 以後そのウィンドウへの読み取りと変更を受け付ける。

### Requirement 8: 予算のゲートと 3 つの OS での観測
**Objective:** As a 保守する開発者, I want 応答の予算が機械的に守られ、実物の振る舞いが観測されていること, so that 回帰と未確認の主張が残らない

#### Acceptance Criteria
1. The Document Session shall 10 万行かつ 30 列のドキュメントについて、読み込み・変更の適用・保存の所要時間を計測可能にし、その判定を CI のゲートに置く。
2. The Document Session shall 3 つの OS のそれぞれについて、ドキュメントを読み込み、変更を適用し、保存した結果を、実際に起動して観測した結果で確認できるようにする。
3. If ある OS での観測を行えないとき、then the Document Session shall その OS について未確認であることを明示する。
