# Brief: form-web-server

## Problem
フォームを作れても、それを他人に届ける手段がなければ「入力を依頼する」という目的が達成されない。同時に、外部からの書き込みを受け付けることは、それまで単一プロセス・単一ユーザーだった前提を初めて破る操作であり、並行制御という新しい問題を持ち込む。

## Current State
form-builder が配信先中立なフォーム定義とレンダラを提供する。配信する手段が存在しない。

## Desired Outcome
アプリからフォームを「公開」すると、同一 LAN 上の端末からブラウザでアクセスして入力・送信でき、送信内容が開いているドキュメントに反映される。公開の開始・停止・アクセス状況がアプリ上で見える。デプロイ作業もクラウドも不要。

## Approach
Rust バックエンドに `axum` を組み込み、form-builder のレンダラを含む静的アセットと送信 API を配信する。アクセスは LAN 限定 + 発行トークンで制御する（個人利用前提のため、これ以上の認証基盤は持たない）。送信内容は schema-engine の検証を通してからドキュメントに追記し、アプリ側の編集と衝突しないよう書き込みを直列化する。

## Scope
- **In**: 埋め込み HTTP サーバ、フォームの公開 / 停止とライフサイクル、フォームページと静的アセットの配信、送信 API と検証（schema-engine 経由）、ドキュメントへの書き戻しと書き込みの直列化、アクセストークンと LAN 限定の制御、接続情報の提示（URL / QR コード）、送信ログとアプリ側への通知、オフライン時 / ポート競合時の挙動
- **Out**: フォームの見た目と定義（form-builder）、静的サイトとしての書き出し（将来のスペック候補）、クラウドホスティング、複数人の同時編集全般

## Boundary Candidates
- HTTP レイヤー（ルーティング・静的配信）と 書き込みドメインロジック（検証・直列化・追記）の分離
- 公開ライフサイクル管理（サーバの起動 / 停止 / 状態）を独立させる
- アクセス制御（トークン・ネットワーク制限）を独立したミドルウェアにする

## Out of Boundary
- フォームのデザインと定義（form-builder が所有）
- 認証基盤・ユーザー管理（個人利用前提のため明示的な非目標）
- インターネット公開・トンネリング（将来のスペック候補）
- 静的サイト書き出しと外部ホスティング（将来のスペック候補）

## Upstream / Downstream
- **Upstream**: document-format, schema-engine, form-builder, app-shell
- **Downstream**: なし

## Existing Spec Touchpoints
- **Extends**: なし
- **Adjacent**: form-builder（レンダラを共有する。レンダラの所有権は form-builder 側）、version-control（フォーム送信をコミット粒度としてどう扱うかを協調して決める）

## Constraints
- LAN 限定。インターネットへの公開は非目標であり、設計上も既定で不可能にする
- 外部からの書き込みが初めて並行性を持ち込むため、書き込みの直列化と、アプリ側編集との競合時の挙動を設計で明示すること
- 送信によってドキュメントが変わるため、version-control の自動コミット方針との整合が必要
- OS のファイアウォールに阻まれるケースの案内をユーザー向けに用意すること
