# 検証の規約

> `app-shell` が確立した、GUI・3 OS・補助プロセスを含む機能の検証の仕方。**残るスペックはここに段を足していく**ため、規約として置く。詳細と実測は `.kiro/specs/app-shell/tasks.md` の 10.x と各 Implementation Notes。**画面を持たないスペックの証拠の取り方は `schema-engine` が足した**（「証拠の取り方」の節）。

## 原則

**主張は「実際に動かして観測した結果」で裏付ける。** 単体テストは回帰の網であって、受入の証明ではない。GUI・配布物・プラットフォーム差を含む主張は、実物を起動して観測する。

そして**観測できないことは正直に書く**。「CI で確認する」は未確認の言い換えであり、確認済みとして扱ってはならない。

## 証拠の取り方（画面を持たないドメインクレート。`schema-engine` が確立）

上の原則は GUI・配布物・3 OS を対象にしている。**画面を持たないエンジン側のスペック**には、それとは別に次の 3 つが要る。

- **実装が先に在るタスクでは、テストの拘束力を変異実験で示す。** 要件を既に満たしていることの確認が目的のタスク（検証専用タスク）では、新規テストが最初から緑になる。**「実装を壊すと落ちる」ことを自分で示すまでは証拠にならない。** 壊すのは 1 箇所（併合・再開位置・規則の分岐・境界の呼び出し）に限り、**必ず元に戻し、戻したことを `md5` と `git diff` で示す**。独立したレビューも 1 つ自力で変異を入れて再現し、元に戻す
- **速度を証拠にしない。証拠は「呼び出しの形」で取る。** 計測は CI ランナーの負荷で揺れるので、「速くなった」「予算内だった」は回帰の証拠にならない。**呼び出し回数・1 回に渡る件数・走査した対象**を数える観測にする（例: 拡張型の一括判定が列ごとに 1 回か。列指定の再検証が指定列だけを走査したか）。**時間予算を持つのは明示された要件だけで、その判定は `scripts/check-bench-budget.sh` のゲートが担う** — 単体テストの中に時間の閾値を置かない
- **標本が識別子（ULID）を含むなら「同一バイト列」を主張しない。** `document-format` の `IdFactory` は時刻を含めて発行するため、標本側では固定できない（公開経路に「識別子を指定して行を作る」口が無い）。**同一**なのは形（列数・行数・構造）と**違反の位置と理由の種別**であり、**同一でない**のは識別子を運ぶ値である。決定性の検査は前者を比較する（生の値を比べない）。プロセスを跨ぐ決定性は、**自分自身のテストバイナリを再実行して**確かめる（同一プロセス内の繰り返しではハッシュの反復順の漏れを検出できない）

## 検証専用のコードの置き場

- **Rust 側**: 非既定の cargo feature `verification-triggers` の下に置く。既定ビルドには識別子すら残らない
- **フロントエンド側**: cargo feature は TypeScript を括れない。**ビルド時の定数**（`vite.config.ts` の `__JXCEL_VERIFICATION__`、検証用は `JXCEL_VERIFICATION_BUILD=1`）で切り、**動的 import ＋ 到達しない分岐**にして静的 import を残さない
- **出荷物に入っていないことを検査で固定する**。Tauri は資産を圧縮して埋め込むので、**バイナリへの `strings` では JS の中身を見られない** — ビルド済み `dist` を見る
- 検証用の形の作り方（`npx tauri build --no-bundle --features verification-triggers`）と出荷物の作り方（`npx tauri build`）は**別物**。混同すると偽の失敗・偽の成功の両方が起きる

## 引き金（環境変数）の語彙

検証専用の入口は**環境変数 1 系統**に集める。機能ごとに新しい仕組みを作らず、**引き金を足す**。既定ビルドはこれらを無視する。

- 起動の振る舞いを変える（初期画面の指定、終了・パニック・ウィンドウ生成失敗の強制、補助プロセスの起動）
- 通知を抑止して時限の経路を踏ませる（描画の不成立）
- 委譲先の判定を差し替える（ウィンドウを閉じる要求の拒否）
- **ドキュメントのセッションの経路を起動の引数から駆動する**（`JXCEL_VERIFICATION_SESSION=open,edit,<行数>,save`。`document-session` が足した）: 起動時に指定された位置のドキュメントを読み込み → **1 回の `edit` で `<行数>` 行を書き換え** → 保存し、状態と閉じてよいかの答えを記録する。記録は `[検証] セッション: ` を行頭に統一した **6 行**（引き金を読んだ / 読み込んだ行数 / 一括の適用を 1 回行った（版・行数・セル数）/ 閉じてよいかの答え（保存の前）/ 保存した（バイト数）/ 閉じてよいかの答え（保存の後））。**5 つの不能な入力**（シート無し / 列無し / 行数 2 未満 / 引き金の行数が読み込み行数を超過 / 回転が恒等）では**適用も保存も行わず**「引き金の走行を完了できなかった」を 1 行残して止まる（成功の記録を偽らない）。**既定ビルドの識別子は 0 件**（`strings -a` の実測。debug と release の両方。検証ビルドは 1 件）。検査器は **3 OS 共用の POSIX sh** の `scripts/check-document-session.sh` であり、段の実体は `scripts/ci/{linux,macos,windows}/verify-document-session.*`、**判定はランナーごとに閉じる**。**記録の開始行数を走行の直前に取り、その後ろだけを数える**（前の走行の完全な記録を置いても緑にならないことを変異で実測した）。起動の形跡を最初に確かめ、保存の実体は検査器が自分で読む（記録のバイト数 == 実際のファイルの大きさ）。**負の対照**は配布物を起動し、非 0 であること**と落ちた理由が「引き金の行の不在」であること**の両方を要求する

**終了前の問いの提示の差し替え口**（`closeVeto.ts` の `installCloseDenialHandler`。`document-session` が足した）。既定は**現行の記録のみ**（`console.warn` の 1 行）であり、**未設定なら差し替え口の追加前とバイト一致**する（app-shell の観測可能な振る舞いを 1 ビットも変えない）。設置は `src/main.tsx` の 1 箇所だけで、判定の往復は `evaluateCloseRequest` に括って `CloseRequested` の購読と `CloseDenial.retry` が**同じ経路**を通る（前の答えを固定しない = 要件 6.7）。**提示はシェルのクロームに 1 点**であり、2 つ目の React ルートは切らない（`createRoot` は `src/main.tsx` に 1 つだけ）。これは環境変数ではない — 差し替えの口そのものは**既定の振る舞いを変えないので出荷物にも入る**（上記の「検証専用のコードは出荷物に入れない」は環境変数と feature の話であり、この口は既定で現行と同一の 1 行を出すだけである）。**差し替えの口は 1 つに限る**（拒否の材料が往復の中にしか無いため、第 2 の口を作らない）。

**引き金は検証の面を広げるためのもので、製品の分岐を増やすためのものではない。** 引き金が無いと踏めない経路は、受入の証拠が無いのと同じである。

## 検査器の規約（`scripts/`）

- **終了コードは 3 値**: `0` = 適合 / `1` = 逸脱 / `2` = 入力が使えない。**入力が無いときに 0 を返さない**
- POSIX sh。**3 OS のランナーで同じものが走る**。メッセージは日本語で、次に取る行動を含める
- **無いことを確かめる検査には負の対照を付ける**（出荷物を渡したら落ちる、等）
- **観測と後始末の共有部分は `scripts/lib/` に置き、検査器はそれを読む**（写すと片方だけ直る）
- 起動したプロセス・展開した一時物は**必ずトラップで片付ける**。残すと後続の段が偽の失敗をする
- 「本当に起動したか」を先に確かめてから結果を判定する。起動していない検査は残存 0 でも緑になる
- **検査器は「その道で使う道具」だけを要求する。** 無条件に道具を要求すると、他 OS の段が**観測の前に 2 で落ちる**（`data-grid` の 9.2 の実測: `DISPLAY` は Linux でだけ要り、`busctl` はアクセシビリティの木を使う道でだけ要る。macOS には `busctl` が無い）。使わない道の道具を要求しない
- **段が作る標本・生成物はリポジトリの中へ置く。** この開発機の `cargo` はコンテナの中で走る shim であり、**バインドされるのはリポジトリだけ**である — リポジトリの外（`/tmp` 等）へ書いた標本は、生成器とアプリで**別のファイル**になる（実測: `/tmp` の標本がアプリから `invalid container: … Could not find EOCD` に見えた）。`target/` 配下に置けば 3 OS のランナーでも同じに動く

**横断の規則（`document-session` の 3.6 が実測で見つけた）: メニュー項目を足すスペックは、項目数と一覧を主張している検査器を同時に更新すること。** `scripts/check-menu-shortcut.sh` は**項目数と一覧の両方**を主張している（配置の記録の `項目数=` 行と、埋め込み Python の `EXPECTED` の辞書。検査器自身が「何項目・どの位置・どの表示名・どの綴り」を要求する）。`scripts/ci/macos/verify-menu-shortcuts.sh` は**項目数と配置の行**を（`for expected in` の一覧で）主張する — `EXPECTED` を持つのは前者だけである。**Windows の段（`verify-menu-shortcuts.ps1`）は項目数を主張しない**（診断の 1 項目の活性化だけを見る）ため、更新が要るのは Linux と macOS の 2 段である。`document-session` は 7 → 9 への増加に合わせて4 行（`EXPECTED` の 2 節 + 配置の 2 行）と `項目数=9` を**同じ作業の中で**更新した — **この 2 つの検査器は「新規」「保存」のメニュー登録の変更のテストそのもの**である（メニューを足すタスクには、この更新までを含める）。**現在の項目数は 13**（`data-grid` の 10.8 が「貼り付け」を足した）。**数を主張している記述は 2 か所（`EXPECTED` と配置の行）× 2 段（Linux / macOS）であり、`macos` の段は数を、`windows` の段は数を見ない。**

## CI の段の規約

- **既存の 3 OS マトリクスに段を足す**。プラットフォーム別に独立した検証系統やジョブを新設しない
- 段ごとに `if: runner.os == '…'` で分け、POSIX スクリプトは Windows でも `shell: bash` を明示する
- **判定はランナーごとに閉じる**。3 OS の値を 1 か所へ持ち寄るにはジョブ間依存が要り、上の規則に反する。**全体としての合否は、各ジョブが自分の担当分で落ちることで成立する**
- **主張は「区切りの後ろ」に限定する**。出力全体を走査すると、前の実行が残した行（検査器の失敗ダンプ等）で錠前が満たされたり壊れたりする。開始位置を記録し、それ以降だけを数える
- **正例と負例の両方を段に持たせる**。落ちない検査器・常に落ちる検査器のどちらでも緑にならない形にする
- **閾値は要件の値を CI から与えない**（引数の既定＝要件値。CI は引数なしで呼ぶ）
- 予算の判定は**最も余裕がないプラットフォームを基準**にする。支配的なコストは画面基盤の初期化であり、こちらの実装ではない
- **非既定 feature の下のテストは、既定のテスト実行では走らない。**`cargo test --workspace` は feature を付けないので、`verification-triggers` の下に置いたテスト（引き金の綴りの受理・初期化スクリプトの組み立て等）は**コンパイルすらされない**。**検証専用のコードを足すタスクは、feature を付けた実行（`cargo test --manifest-path src-tauri/Cargo.toml --features verification-triggers`）まで含める** — 含めないと、そのテストはどこでも一度も走らない。**現状の CI は既定の実行だけであり、feature 付きの実行は段に無い**（`2026-09-17` の同期で判明した未消化の差分。段を足すか、検証用のビルドの段でその振る舞いを確かめるかは未決定）

## ランナーの扱い

CI ランナーは要件が想定する環境（SSD・4 コア以上）より**弱い保守的な代理**である（private リポジトリのランナーは 2 vCPU、macOS は 3 コア）。**弱いことを理由に閾値を緩めない** — 弱い環境で通れば要件の環境でも通る、という向きの代理として使う。

## この環境での実測手段（開発機）

GUI を含む主張は、まず開発機で実測する。CI と同じものを走らせ、**残る差（OS・署名・ランナー固有）を明示する**。

- 起動と描画: 仮想ディスプレイで配布物を起動し、ウィンドウの存在をツリーから、画素を画像から確かめる。**ウィンドウが現れないときは、まず表示サーバの種類を疑う**（合成側に行くとツリーに現れない）
- キー入力: 一部のツールキットは合成キーの標準経路を受け取らない。**届かない場合は配送経路を変える**（実際に届いた方法を記録に残す）
- UI の中身（メニュー・画面の文言・活性状態）: **アクセシビリティの木**を読むのが最も強い。実アプリのメニュー項目の列挙と活性化、画面の見出しの読み取りに使える
- **ログと記録を一次証拠にする**。アプリ自身が「何をしたか」を記録に残す設計になっているので、対象ウィンドウ・判定・版の一致は記録行で示せる
- **画面の中の実測を 3 OS で判定するときは、アプリ自身に記録を書かせる**（`data-grid` の 9.2 が確立）。アクセシビリティの木を持つのは **Linux のランナーだけ**である — AT-SPI は D-Bus 上の仕組みであり、macOS の WKWebView と Windows の WebView2 は別の API を使い、**CI のランナーにはその権限も無い**。したがって「フロントエンドが計算した値を検査器が読む」形にすると、判定は Linux でしか成立しない。**値をアプリの記録へ 1 行書かせ、検査器は記録を読む**（`aria-label` にも同じ実測を出してよいが、それは人が見るためであり判定には使わない）
- **観測の行は機械可読な `key=value` にし、人が読む文言と分ける。** 判定は記録の `key=value` だけで行う。**観測できなかった項目は理由を書く**（無言で飛ばさない）。**行は部分でも書く**（途中で止まっても、それまでの実測が読める）。`data-grid` の 9.2 の記録は `診断の記録へ 1 行 + 項目ごとに 1 行` の形である

## ローカルで閉じられないもの

以下は**ローカルでは確認できない**。残るリスクとして明示し、CI の実行で確認する。

- macOS / Windows の実行時の振る舞い（この 2 つは実行環境が無い。クロスコンパイルの確認まで）
- コード署名とバンドラによる書き換え、配布形式ごとの配置と起動
- プロセスグループ / Job Object の強制終了、OS ごとのプロセス名の見え方
- 3 OS の配布物生成と成果物の取得、監査ジョブ
